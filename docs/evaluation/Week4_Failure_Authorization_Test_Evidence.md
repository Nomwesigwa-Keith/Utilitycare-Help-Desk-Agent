# Week 4 Failure / Authorization Test Evidence

## Purpose

This note records deliberate testing of the two approved tools
(`get_outage_status`, `draft_ticket`) and the tool-calling orchestrator
against four required failure categories: missing parameters, unauthorized
requests, a tool that is "down", and a weird/unexpected tool response.
Full machine-readable results are in
`evidence/traces/week4_failure_authorization_results.csv`, generated by
running `python -m tests.test_failure_authorization`. This note interprets
those results against the documented behaviour in
`docs/requirements/Tool_Catalogue_and_Schemas.docx`.

## Method

10 cases were run directly against the real `src/tools.py` and
`src/orchestrator.py` code (no mocked orchestrator, no LLM call). Two of the
four categories — a tool being "down" and a tool returning a malformed
response — cannot currently be triggered by any real input, because
`tools.py` has no code path that simulates a backend outage. For those two
categories the tool functions referenced in `TOOL_REGISTRY` were temporarily
replaced with functions that raise a simulated backend error or return a
malformed payload, the orchestrator was exercised exactly as an agent would
exercise it, and the original functions were restored immediately after.

## Result summary

| Category | Cases | Boundary held | Gaps found |
|---|---|---|---|
| Missing parameters | FA-01 – FA-04 | 4 | 0 |
| Unauthorized request | FA-05 – FA-06 | 2 | 0 |
| Tool "down" (simulated) | FA-07 – FA-08 | 2 | 0 |
| Weird/unexpected response (simulated) | FA-09 – FA-10 | 0 | 2 |

**8 of 10 cases held the documented boundary. 2 cases exposed a genuine gap.**

## Findings

**Missing parameters and unauthorized requests are handled correctly.**
The orchestrator rejects calls with missing required fields before the tool
ever runs (FA-01, FA-03), and the tools themselves reject invalid values
such as an empty `area_code` or an out-of-enum `priority` (FA-02, FA-04).
An unregistered tool name is rejected outright (FA-05). An attempt to force
a drafted ticket straight to `"submitted"` status fails (FA-06) — though it
is worth noting this currently succeeds only because `draft_ticket()`'s
signature has no `status` parameter, not because of an explicit
authorization check. If the function signature ever changes to accept more
flexible input (e.g. `**kwargs`), this protection would silently disappear.

**Simulated backend outages are converted to clean errors, not crashes.**
When `get_outage_status` or `draft_ticket`'s backend is simulated as
unreachable, the orchestrator's generic exception handler converts the
failure into a `ToolExecutionError` (FA-07, FA-08) rather than letting an
unhandled exception propagate. This matches the spirit of the catalogue's
documented behaviour, although the specific fallback actions it describes
(e.g. "proceeds with general troubleshooting guidance", "draft held
locally") are agent-level behaviours that live in `src/agent.py`, not in
the tool/orchestrator layer tested here, and were not verified by this
test.

**Gap: malformed tool output is not validated and passes through as a
success.** `orchestrator.py` returns whatever a tool function returns with
no check against the tool's documented output schema. When
`get_outage_status` was made to return an unexpected shape (FA-09) and when
`draft_ticket` was made to return a plain string instead of the documented
dict (FA-10), both were reported back as `"success": true` with the
malformed data intact. The Tool Catalogue documents that a malformed or
unrecognised response shape should be treated the same as a
service-unavailable failure; the current code does not implement this.

## Recommendation

Add an output-schema check to `execute_tool_call()` in `src/orchestrator.py`
(e.g. verifying the returned dict has the exact keys/types documented for
that tool) so a malformed response is converted to a `ToolExecutionError`
instead of passing through as a success. This is a good candidate for the
Week 7 Failure Catalogue if not fixed before then.
